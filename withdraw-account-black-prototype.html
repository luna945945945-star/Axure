适用系统：V1 后台 · 风控管理　|　版本：V1.0
需求目标
  • 拉黑提现账号后禁止提款：银行卡 / 电子钱包 / 加密货币 / UPI 等提现账号被拉黑后，无法用于提现；即使换一个新会员 ID 绑定同一账号继续套利，同样无法取款。

  • 两者互为支撑：绑定历史提供发现线索，黑名单提供处置手段。

二、口径定义与业务规则
2.1 归一化与匹配口径
  • 归一化规则（唯一一套，不区分账号类型）：去除全部空格 → 去除全部连字符 → 转为小写。
  • 录入侧与提现校验侧必须共用同一个归一化方法，不得各自实现。两侧规则不一致会导致拉黑后拦不住且不报错。
  • 匹配方式：拿归一化后的完整账号值做精确匹配。系统不维护「提现账号类型」这一概念——录入、匹配、列表、导出、导入全链路均只使用账号值本身。
  • 不去除点号：. 在邮箱型账号与 CPF（123.456.789-00）中有语义，去除会造成不同账号相互命中。
录入 / 绑定的原始值归一化结果是否互相命中
6238 8812 3434 56786238881234345678命中
6238-8812-3434-5678
RajKumar@YBLrajkumar@ybl命中
rajkumar@ybl
  • 同一账号跨通道天然命中：同一个 UPI ID 无论从 UPI / NewUPI / FastUPI 绑定，归一化结果相同，命中同一条黑名单记录。USDT 两个通道同理。这是归一化的自然结果，不需要额外配置。
  • 存量数据需一次性回填：上线时按本规则重算所有已绑定账号的归一化值，否则存量数据的聚合统计不准。
2.2 拉黑生效口径
  • 拉黑后的效果仅限：禁止使用该账号提现。不影响登录、投注、充值。
  • 不拦截绑定：黑名单账号仍可被任意会员正常绑定，只有在发起提现时才拦截。此为刻意设计——绑定即报错会让套利者立刻察觉并更换账号，情报链断裂；放行绑定可持续沉淀关联关系。
  • 在会员端即拦截：拉黑后该提现账号下一次提现即被拒绝，后台不会产生新的提现订单。
  • 支持预拉黑：允许对尚无任何会员绑定过的提现账号直接加入黑名单（风控提前拿到的可疑名单）。日后有会员绑定该账号并发起提现时同样被拒绝。
  • 解除拉黑：该提现账号恢复正常提现。
  • 已出款成功的历史订单不做追溯。
  • 拉黑 / 解除 / 导入 / 导出均需记录操作人与操作时间，并写入后台操作日志。
2.3 累计绑定次数口径
  • 只统计「绑定」动作的累计次数：解绑不减少，后台修改不计数。
  • 一个提现账号被 3 个会员先后绑定过（中间各有解绑），其累计绑定次数为 3。
  • 实时更新：会员绑定完成后该数值立即变化，列表与明细始终一致，无延迟。
  • 预拉黑的账号（从未被任何会员绑定）该数值为 0，因此在默认筛选（≥ 2）下不出现在列表中，需把筛选放开到 1 或按账号 / 会员 ID 查询才能看到。
  • 提现账号的黑名单状态与其统计数据属于同一份账号数据：在任一页面拉黑或解除后，另一页面立即同步，不存在两边不一致的中间态。
2.4 绑定历史记录规则
  • 会员的提现账号发生绑定、解绑、后台修改时，均留存一条历史记录，解绑后记录永久保留。
  • 记录内容：发生时间、动作、会员 ID、会员账号（注册手机号或邮箱）、收款人姓名、提现账号值、操作来源、操作人 / 工单号。
  • 操作来源共三类，对应 V1 现有的三条实际操作路径：
操作来源对应动作操作人 / 工单号说明
会员自助绑定会员 ID会员在客户端自行绑定提现账号，操作人记该会员的会员 ID
客服工单解绑工单号V1 的解绑走客服工单，客户端没有会员自助解绑入口；批量清理某会员的某类提现账号也由工单触发
后台修改后台修改、后台新增 / 删除后台账号客服 / 管理员在后台直接修改收款人姓名、IFSC、UPI ID 等
  • 会员账号取会员的注册账号——V1 注册方式为手机号或邮箱二选一，故该字段为手机号或邮箱。
  • 查询支持两个维度：
    · 以提现账号为主体——给定一个账号，完整看到「谁、在什么时间绑定、什么时间解绑」的全量记录，跨会员、跨通道、跨时间；
    · 以会员 ID 反查——给定一个会员，列出其历史绑定过的全部提现账号。
  • 银行卡、电子钱包、加密货币、UPI、PIX 全部纳入，规则一致。
  • 唯一绑定前提：V1 已有全站唯一校验，同一账号在同一时刻只有 1 个会员处于绑定中；历史上可被多个会员先后绑定（绑定 → 解绑 → 再被他人绑定）。因此「累计绑定次数 > 1」表示的是时间维度上的先后关系，不是同时绑定。
  • 例外与告警：UPI 三代等通道的唯一校验口径不一致，存在同一账号在两个通道各被一个会员绑定的缺口。此类情况在列表「当前绑定会员」列打「⚠ 跨通道并存」告警，供风控识别既有脏数据。
  • 历史记录为只读，任何角色不可编辑或删除。
三、边界与限制
#边界说明
B1历史数据不可追溯上线前已解绑的记录无法还原，绑定历史自上线日起累计。上线时对当前仍在绑定状态的账号补录一条「绑定」记录，时间取原始绑定时间。需提前与运营 / 风控对齐预期。
B2不拦截绑定黑名单账号可被正常绑定，会员在绑定环节无任何异常提示。若后续需要改为绑定即拦，属独立需求。
B3只拦账号、不连坐会员本期只限制被拉黑的账号本身，不会自动限制曾绑定过该账号的其他会员。换号套利者用同一账号提现会被挡住，但换成另一个新账号提现仍可放行——需风控发现后再拉黑新账号。
B4不做片段 / 主体提取匹配只按归一化后的完整账号值精确匹配，不做子串、片段或「数字主体提取」的关联（如 9821034567 不会去关联 rajkumar9821@ybl）。此类嫌疑需人工通过账号模糊搜索排查。
B5归一化统一转小写加密货币地址等大小写敏感的账号也会被转小写后比对。因录入与校验两侧做相同变换，同一账号的匹配不受影响；仅存在「两个不同地址仅大小写不同」时相互命中的理论可能，实际不会自然发生。
B6单站范围V1 为单站模式，黑名单与绑定历史均在本站范围内生效，不涉及跨站点共享或查询。
B7不处理在途订单拉黑只对之后发起的提现生效。拉黑前已提交、仍在审核 / 出款流程中的订单不受影响，按原流程处理——本期不做联动驳回，避免与出款审核流程耦合。如需拦截，由审核人在出款审核环节人工处置。
B8后台人工出款不受拦截后台代客出款、人工确认出款不经过会员端提现校验，黑名单对这条路径不生效。本期不做后台出款侧的校验改造，列为已知风险，由出款审核人在操作时自行留意。
此路径需人工发起，非会员可自助触发，风险敞口可控。
B9仅覆盖提现收款账号不涉及充值收款账号、C2C 卖家账号等其他账号体系。
B10两侧归一化必须一致录入侧与提现校验侧必须调用同一个归一化方法。若两侧规则不一致，表现为拉黑成功但拦不住，且无任何报错与日志——属静默失效，最难排查。上线前需专项验证。
B11不做模糊 / 片段匹配本条约束的是拉黑命中判定：一律按归一化后的全量精确匹配，不支持按账号片段拉黑（短数字片段做包含匹配会大面积误伤正常会员）。
后台列表的提现账号搜索框仍支持模糊查询，仅用于查找，不影响拦截判定。
B12统计与明细的一致性校对累计绑定次数为累加值，正常情况下与绑定明细完全一致。为防止异常写入（如绕过系统直接改库）造成数值偏差，需提供一个后台可手动触发的「绑定次数校对」维护动作，按明细重算并修正。低频使用，不做定时执行。
B13掩码与权限账号全量值需具备相应数据权限方可展开查看；黑名单的添加 / 解除 / 导入 / 导出需分别配置权限点。
